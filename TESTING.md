# Testing

There are three layers. Run them in order, because a failure lower down explains a failure higher up.

## 1. Unit tests on the Mac

```sh
scripts/build-wireguard.sh   # once, and after a change in WireGuard/. xcodegen runs it too
swift test
```

They need no device and no internet. They cover:

- WireGuard keys and configs: key pairs, address allocation, the client config text, where each device's config points (saved with it, and a setup saved before that still loading), and a Keychain error never replacing the saved server key.
- Pausing a device (`PauseTests`): saved with its reason and kept after a relaunch, a setup saved before pausing still loading, a reason from a newer version still reading as paused, a pause that can't be saved changing nothing and saying so, the device sent to Go paused and kept on the real server, and never counted as connected while its tunnel is up, on screen, in the background and in the Shortcuts actions, but connected again at once on Resume. Pausing tells no notification and doesn't ask for permission to. And the words its row and screen use (`DeviceStatus`).
- WireGuardServer.swift through the C API into the real Go server (the xcframework's macOS slice): start and stop, a bad address or a port in use coming back as an error, short keys refused before Go reads them, peers Go refuses, and two junk handshakes showing up in the snapshot as a config that no longer works, gone once the server stops.
- The server's counters: no device counting as connected before its first handshake, and traffic totals that never go backwards across restarts.
- The hotspot lifecycle in `HotspotSession`, round by round: the server starts when the hotspot appears and stops when it goes or changes, a failed start is tried again, a setup problem shows before a start problem and a stale start error clears with the hotspot, a refused device list restarts the server, a rename or removal that couldn't be saved says so until a change saves, the config page starting and stopping with the server and starting again after a failure, the 10-minute keep-alive wait on and off screen, the add window (the code let in only while Add a device is open and for 10 minutes after it closes or Tether leaves the screen, a new code each time it opens after that, a new code that can't be saved leaving none rather than the old one, also after a relaunch, and a claimed device working on after the window), the background claim and read of who is connected, and the speeds. And where devices reach Tether on a carrier that gives the iPhone IPv6 only: the IPv6 address in use kept through the hotspot going off and on and a relaunch, Tether listening on 172.20.10.1 too, for a Windows PC that takes IPv4 there (#98), a download over IPv4 pointing at 172.20.10.1 and one over IPv6 at the IPv6 address, each device keeping the address its config points at (from the QR code, the page, or when it connects, by where its handshake came from), and a device saying it needs a new config while Tether doesn't listen where it points, never for one on 172.20.10.1, never on a usual carrier and never for a device saved before Tether kept it. And a config that no longer works (a device knocking with a code that expired, after it was removed, or with old server keys): shown for a minute after its last knock, gone with the hotspot, and read by the config page when it's asked, off screen too.
- The config page: what it reads from a request (only the request line, the path without the query), the headers on every answer (no caching, no sniffing, no scripts, closed after it), the config handed out only while Tether is on screen and the add window is open, by the clock, a download listing the device and making a new key for the next one, a download that couldn't be saved handing out nothing, and the line for a config that no longer works coming first on every page. The real listener runs on loopback, also on 127.0.0.1 and ::1 at once, and one that fails stopping both so the next round tries again: one answer per connection, a request in pieces, a head over 8 KB, a connection that sends nothing, a port in use, and a restart on the same port.
- The parts the session is made of, each on its own: the add window's clock (`AddWindow`: open while the sheet is on screen, 10 minutes after it closes or Tether leaves the screen, closed at launch), what the config page answers from what the session tells it (`ConfigPageHandler`: the state the page says, a download handed back to the session to save, the same download again for the same client within a minute, a failure logged once, and the line for a config that no longer works: for the device that knocked, by its address with or without a port, also when another device knocked since, or for any device with old server keys, never for a request from where Tether listens, and gone a minute after the last knock), and the speeds from two reads of the counters (`TrafficSampler`).
- Each device's data per month (`MonthlyUsage`, and in `HotspotSession`): each read adding what the counters grew by and the same read twice adding nothing, counters that start over after a relaunch counting in full, the month turning over on the 1st in the iPhone's time zone, months with no read rolling over when shown (two months on, both empty), a clock set back adding to the month it says and never rolling back, a removed device dropped, a locked Keychain dropping nothing, saving at most once a minute and reading it back after a relaunch, and a device removed while the hotspot is off handing nothing to the next device given its address (`WireGuardServer`). And when each device last connected: each read's handshake kept, also after a clock set back, kept through the hotspot going and a relaunch, dropped with the device, none for data saved before Tether kept it, and said as Never, Today, Yesterday or the day in the region's clock (`Format`).
- A device's data limit (`LimitTests`, `DataLimit`): saved with the device and the pause at it read back (`{"why": "limit"}`, an older setup has none), the menu's choices and an amount typed in GB, told once at 90% and paused and told at the limit, a pause that can't be saved told only once it's saved, a pause by you left alone, resumed at the limit going over it until the 1st (and not when the 1st already let it go, or the resume wasn't saved), Pause keeping a pause at the limit, the 1st letting it connect again with the hotspot on or off, a new limit counting at once and forgetting a resume and what was told while the same limit picked again forgets nothing, and each limit notice told once in the background behind its switch.
- The DNS server for new devices (`DNSChoice`): each choice's servers, a second one with each preset, one or two IPv4 addresses typed under Other and anything else refused (IPv6, a name, three addresses), an unusable Other giving Cloudflare so no config goes out without a DNS server, the saved choice and an unknown one, and each config the session makes (the QR code's, a download) naming the server picked at that moment. Control D (#100): the profile typed as a DoH link, with a device name or not, or a resolver ID alone, anything else refused and giving Cloudflare, its config naming 10.7.0.1, and the server told where lookups go at each start and each change of the setting (`WireGuardServerTests` checks Go takes both kinds).
- Stopping when idle (`IdleStop`, and in `HotspotSession`): only in the background while sharing, counted from the last connected device or from leaving the screen, Never by default, the server, the page and the sound stopped at once and kept stopped with the hotspot on, and opening Tether or Start Tether sharing again. Notifier tells each stop once, with its time, behind its own switch.
- Notifications (`Notifier` and `NoticePoster`): a device told by name when it connects, and when it leaves only once it has been gone 3 minutes, one device at most once in 5 minutes, nothing on screen and nothing told again that the screen showed, the hotspot going told as each connected device disconnecting after 3 minutes (its network also goes when the last device leaves, so Tether can't tell the two apart), WireGuard stopping told after a minute with the devices that were connected, the build expiring told once a day, a notice that waits 3 minutes ahead while Tether shares and is pushed back every minute, so it shows only if Tether stops (taken away when sharing stops, its switch goes off, or Tether launches again), a switch for each kind, and permission asked on screen when something happens there that would be told in the background, once, with nothing posted before that or after a no.
- Add a device's steps (`AddDeviceProgress`): a download ticks step 2 and waits for the tunnel, a scan ticks both at the first handshake, only the code's own device counts, and the screen stays on until it connects. And what a Bonjour browse's state says about Local Network access, and that no check runs before the first launch's screen about it is through (`LocalNetworkIntro`), then every one does, and the screen shows once.
- The log Settings shares (`DebugLog`, `LogRedaction`): each line with its time, the Go server's lines in their place with their own times (taken through the C API, see `WireGuard/golog.go`), the lines of an earlier launch kept, two files of 256 KB at most, a real client config written through it leaving no piece of a key on disk, and what a line leaves out: WireGuard keys in base64 and hex, IPv6 addresses after their first two groups (also next to a port or a word), and public IPv4 addresses after their first two numbers, while the hotspot's, the tunnel's and other private addresses stay.
- The ready device (not listed until it connects, then listed and replaced by a new one, and replaced on demand, with no ready device at all when the new one can't be saved), the build expiry warning, when the keep-alive sound plays, how bytes and speeds read, and what the Shortcuts actions say.

The WireGuard server has its own Go tests. CI runs them at full size, then again under the race detector:

```sh
go -C WireGuard test ./...
go -C WireGuard test -race ./...
```

CI also fuzzes the UDP replies for 30 s and checks for known vulnerabilities. Locally:

```sh
go -C WireGuard test -run '^$' -fuzz FuzzReplyPackets -fuzztime 30s ./...
go -C WireGuard run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
```

The fuzz test sends any payload from the internet through `replyPackets` and checks the fragments are valid IPv4 that put the datagram back together exactly. `govulncheck` fails only when Tether's code can reach a known vulnerability.

They run a real WireGuard client (wireguard-go with its own netstack) against the server over loopback: TCP and UDP through the tunnel, an unknown key getting nothing, sharing off, a removed device locked out and its connections closed, a paused device keeping its handshake and session while it gets no TCP, UDP or ping through, its connections closed on both sides, its count kept, the others untouched, a paused router's clients stopped too and a paused device never taking the router's role (`pause_test.go`), a router's clients sending from their own private addresses (and a plain device or a public address refused), Close during UDP traffic (a deadlock once), full-cone UDP (a reply from an address the device never contacted gets through, the way a call connects), replies bigger than the tunnel MTU arriving in IPv4 fragments, ping through the tunnel, TCP and UDP reaching IPv4 hosts through the carrier's NAT64, and a cone's own socket holding its IPv4 port. `golog_test.go` covers the lines the server keeps for the shared log: only the ones that say something, a device named by its tunnel address and never by a piece of its key, a line that repeats counted once a minute, and the message Swift reads. The client's netstack refuses to send to 127.0.0.1, so the tests dial a documentation address (198.51.100.7) and swap the server's dialer to reach the local test listeners.

Scenario tests run many devices at once, the way people use Tether:

- `many_test.go`: eight devices downloading and pinging together, and a travel router next to direct devices.
- `dualstack_test.go`: the server on 127.0.0.1 and ::1 at once (172.20.10.1 and the IPv6 address on an IPv6-only carrier, #98), a device on each, one moving from one to the other, an address that can't be listened on failing the start (the next round tries again), and replies going out of the socket of the device's family.
- `dns_test.go` (#100): a lookup to 10.7.0.1 answered through a DoH server over HTTP/2, over UDP and TCP, with the ID put back and the DNS bytes counted as the device's, an answer too big for UDP cut with TC set, a paused device and a server without an upstream answering nothing, a plain server standing in for 10.7.0.1 over UDP and TCP with its replies coming from 10.7.0.1, a failed connection asked again, an error answer not, a slow server freeing its place under the cap, the cap, Close during a lookup, the device list's `dns`, and a fuzz test of the cutting.
- `traffic_test.go`: uploads and downloads both ways with checksums, a page-load burst, a DNS storm, a call next to a big download, the biggest unfragmented UDP, and a reconnect from the same port right after the host closed.
- `failure_test.go`: far ends that refuse, never answer, close or reset mid-transfer, half-closes both ways, a network that comes up late, and a device sending as another.
- `lifecycle_test.go`: the hotspot going off and on, a device roaming to a new port, sleep and wake, the same config on two devices, devices added and removed while others stream, nothing left behind, and 253 devices configured.

Under `-race` gVisor runs about a hundred times slower, so the busiest tests do less then (`raceEnabled`, see `race_test.go`), and the scenarios whose goroutines meet the way other tests' already do don't run at all (`fullSizeOnly`). The run without `-race` does every test at full size.

Measurements that depend on this computer's speed, or wait on real WireGuard retries, run only with `LOAD=1` and without `-race`:

```sh
LOAD=1 go -C WireGuard test -run TestLoad -v ./...
LOAD=1 DEVICES=32 go -C WireGuard test -run TestLoadManyDevices -v ./...
```

They print throughput and fairness with `DEVICES` devices, ping times while another device downloads (`STREAMS`), memory with devices at their connection cap (`EACH`), a far end that never answers, and two cases that need 15 s of WireGuard retries. Both ends run on this computer, so they show the server's limits here, not the iPhone's.

## 2. UI tests on the simulator

```sh
xcodegen generate
xcodebuild test -project Tether.xcodeproj -scheme Tether \
  -destination "platform=iOS Simulator,name=<a simulator>" -derivedDataPath .build-sim -only-testing:TetherUITests
```

XCUITests in `UITests/` walk every screen and flow of the app: the status card, the speed and the device list on the main screen, each row's data this month, a device's screen with its data this month (down and up, or Not used this month) and last, when it last connected while it isn't (not while paused), its limit's meter and footer, and the Limit menu with Other amount, Add a device (the button, and the sheet with its steps on a line, the code for a phone, and the page's address, its copy button and the shared file for a computer, and how long the code and the file work), one device's screen (Connected or not, Pause under the status with its footer, Paused with Resume in the same spot and Connected again after it, renaming, removing with a confirmation, and saying when either couldn't be saved, or when its config points at an old address), the WireGuard problem section, the Local Network warning on the status card and in Add a device's last step, the first launch's screen about Local Network (only its Continue closes it), the line about a config that no longer works on the main screen and in Add a device's last step, the Settings sheet behind the gear (the idle stop menu with its four choices and the choice kept, a switch for a device nearing or reaching its limit, the DNS menu for new devices with its six choices kept after closing, Other's address field saying what new devices get until it holds one or two IPv4 addresses, and Control D's profile field doing the same until it holds a profile, then its own footer, a switch for each kind, all on, a switch that stays off, the Allow button before Tether asked, what it says when notifications are off in Settings, Share the log above the source link and the share sheet it opens, the version and when the build stops the filled buttons' contrast read from the screen in both appearances, large text and dark mode. They need no device and no network. A demo launch never connects a device, so claiming the ready device is covered by the unit tests, and the sheet's waiting and connected steps by two demos that follow a listed device.

Run them on the oldest and the newest iOS you can, since iOS versions differ in small ways (section headers in capitals or not, a dialog with or without Cancel). Actions > UI tests runs them on iOS 18.5 on an iPhone SE, the smallest screen, and on the newest iOS GitHub's runners have. iOS 17, the oldest Tether supports, isn't available as a simulator for Xcode 27 or on GitHub's runners, so check it on a phone. For an iOS that GitHub's runners don't have yet, run the command above on a Mac with that simulator (`xcodebuild -downloadPlatform iOS` downloads the newest).

A simulator has no Personal Hotspot and nothing to share, so each test launches the app with `-TetherDemo <scenario>` (see `Sources/DemoMode.swift`). The scenarios are fixed fake states: `waiting`, `localNetworkIntro` (the same on the first launch: the screen before iOS asks for Local Network access), `noDevices`, `sharing` (devices iPad connected and Windows PC not, and a speed), `wireGuardLocked` (the Keychain is locked: WireGuard shows its problem and there is no Add a device button), `wireGuardLockedWaiting` (the same with the hotspot off: the problem shows from launch), `wireGuardNeedsReset` (the saved WireGuard keys can't be read, so only "Start over with new keys" gets past it, and then Add a device appears), `wireGuardUnsaved` (a first launch whose new keys can't be saved: no Add a device button and WireGuard isn't running), `qrCodeUnsaved` (sharing, but nothing can be saved: the section for the next device says why there's no code, and a device's screen says a rename or removal couldn't be saved), `expiring` (sharing, two days before the build stops opening), `notificationsOff` (sharing, with notifications off for Tether in Settings), `notifying` (sharing, it asks for permission on screen through the real notification center, and leaving the screen posts one notice), `notificationsScreen` (sharing, opened on the Settings sheet with notifications allowed, for the screenshot), `localNetworkDenied` (sharing, but Local Network is off: the status card says Devices can't connect, and so does Add a device's last step), `staleConfig` (sharing, and a device keeps trying to connect with a config that no longer works), `addDeviceScreen` (the hotspot on and no device, opened on the Add a device sheet, for the screenshot), `addDeviceComputer` (the same with Computer picked), `addDeviceComputerIPv6` (the same on a carrier that gives the iPhone IPv6 only: 172.20.10.1 first, then the IPv6 address for a Mac, (sharing, but the Windows PC's config points at an IPv6 address the iPhone had before, so its row and its screen say to add it again), and `paused` (sharing, but the iPad is paused: its tunnel is up, its row says Paused, and it doesn't count as connected). The settings of a demo launch (the notification switches, the idle stop and the DNS server) live in their own UserDefaults, and its log in its own folder, both emptied at each launch. The WireGuard setup lives in an in-memory store in a demo launch, never the Keychain. A demo launch runs the real session once against stand-ins for the server, the config page and the sound (`Sources/Fakes.swift`, which the unit tests use too), so a screen shows only what the session publishes. It starts no real server or audio, and no watcher or sampler. The code is `#if DEBUG`, so a Release build does not contain it. A launch without the argument is the real app, and `NormalLaunchTests` checks that. It counts the Local Network screen as done (`-localNetworkIntroduced YES`), since the simulator keeps whether an earlier run tapped Continue, and one test launches with `NO` to see it.

## Things we learned the hard way

- **A test build replaces the installed Tether.** Build it with the same bundle ID as the installed copy, or it installs next to it with new WireGuard keys, and every device has to be added again.
- **A media services reset is only reported to an app that uses audio again.** When the media server dies, the silent sound stops, and an app in the background without sound is suspended within seconds. `mediaServicesWereReset` comes only after the app touches audio, so waiting for it waits forever. `KeepAlive` asks for background time as soon as the services are lost, and starts a new player every second until one plays. Killing `audiomxd` alone (`pymobiledevice3 developer dvt kill`) is not the same test: Tether survives that even without the fix, so use the Settings button.
